# 鸿爪录实现路径

> 最新接口约定：数据结构以 `../府库/实现-府库.md` 为准。改名历史保存于 log.result，当前状态保存于 members，不再建立 nickname_events/tasks/outbox。memento 只生成文件和预制消息，返回 upload_file、send_message 动作，由 Main 统一调用发送子函数；下文初稿中“模块自行上传/通知”和 delivery_owner=module 已废止。导出后返回业务成功，上传及通知状态由 Main 写入同一任务日志。

未实现。本文按当前修改后的代码结构、标准 IO 和执行流程补齐实现初稿，随后逐项讨论。用户已定规则直接执行；新增算法阈值、表结构和异常处理标为初稿方案，不代表已经确认或通过 NapCat 测试。

## 1. 目标与边界

发现群成员昵称变化后，以用户 ID 确认身份，通过本地分词得到不超过六段，参考旧槽位对齐后写入原有工作簿，再上传群文件并发送预制消息。首次按顺序填槽；后续删除中段不能把后面的槽位全部前移。

- 不使用 AI 分词，采用 jieba、自定义词典和本地合并规则。
- 当前先处理一个群，未来各群的数据与工作簿分开保存。
- 业务任务进入统一队列，处理完一个再处理下一个；消息接收和入库持续进行。
- 保留完整原昵称、新昵称以及拆分结果，不能只保留 Excel 槽位。
- 首次建立记录的备注写“初创”，不发送改名通知。
- 数据库字段及算法初稿在后文给出，后续逐项讨论后冻结。

## 2. 代码结构

以下为计划中的代码目录，本文不创建这些代码文件：


| 文件 | 职责 |
|---|---|
| `memento.py` | 校验输入、查询旧昵称、调用分词与写表、协调数据库记录、上传群文件及发送预制消息 |
| `nickname_dictionary.txt` | 保存固定称呼、群内短语等自定义词条，供本地分词使用 |
| `nickname_segmenter.py` | 完整昵称转为按原顺序排列、最多六段的列表 |
| `align_slots.py` | 参考旧槽位，输出保留、修改、删除、新增后的六槽及变化记录 |
| `segmentation_rules.json` | 保存合并规则、对齐阈值和算法版本 |
| `write_in_excel.py` | 在原有工作簿追加成员记录及总变迁记录，保留历史内容和样式 |
| `write_in_excel.md` | 解释工作表定位、实际记录行查找、样式复制、保存及异常处理原理 |

本地分词文件不命名为 `jieba.py`，避免与第三方 jieba 包混淆。子函数目录统一使用 `son_function`。上传和预制消息的业务步骤放在 `memento.py`，调用共享 OneBot 客户端，不额外拆业务子函数。

## 3. 标准IO

Main 统一接收事件中的群号、用户 ID、消息 ID（如有）、触发类型、触发时间及事件内容。普通消息经过 `Function/intention/intention.py` 识别后才得到 `opt`、`params`；昵称变更属于系统事件，直接分发为 `memento`，无需 AI 识别。

最小业务接口：

```python
from Function.memento import memento

if opt == "memento":
    await memento.run(
        group_id=request["group_id"],
        user_id=request["user_id"],
        new_nickname=request["payload"]["new_nickname"],
        observed_at=request["triggered_at"],
        observation_seq=request["receive_seq"],
        task_id=request["task_id"],)
```

| 输入 | 来源与用途 |
|---|---|
| `group_id` | 由 Main 从可信事件中取得，用于选择本群数据及工作簿 |
| `user_id` | 改名者的稳定 ID，用于定位成员，不使用昵称代替 |
| `new_nickname` | 本次实际观察到的完整群昵称 |

初稿额外传 observed_at（带时区时间）、observation_seq（接收序号）、task_id（稳定 UUID），用于排序、去重和恢复。无法取得实际改名时间时，只记录发现时间，不冒充准确改名时间。

标准输出：

```json
{"status":"ok","result_id":"变更UUID","reply_text":null,"delivery_owner":"module","error_code":null}
```

未改变昵称返回 skipped；未能可靠分槽返回 error，error_code 为 nickname_alignment_required。上传与预制通知在模块内完成，Main 不再重复发送。

## 4. 执行流程

```text
接收并保存昵称观察事件
→ 加入统一业务队列
→ Main 调用 memento.run
→ 按群号、用户 ID 查询成员及最近昵称
→ 首次观察：建立基线，写“初创”，不发送改名通知
→ 新旧昵称相同：结束
→ 新旧昵称不同：执行本地分词、旧槽位对齐及校验
→ 数据库保存变更记录、分词结果和待导出状态
→ 修改现有鸿爪录.xlsx
→ 标记导出完成
→ 通过 OneBot 客户端上传到对应 QQ 群
→ 上传成功后发送预制消息
→ 更新任务处理状态
```

初创的 old_nickname 为 null，成员表备注为“初创”；注释表变迁为“初创：{完整昵称}”，修改记录为“初创”。初稿仅本地更新，不主动上传；下一次真实改名时一起上传。

昵称检测初稿为消息名片观察加每 10 分钟一次成员列表同步，实际字段需 NapCat 实测。字段缺失不等于用户主动清空昵称。队列按观察顺序处理，陈旧事件不覆盖较新的观察状态。

## 5. 分词

建议接口：

```python
def split_nickname(nickname: str, old_slots: list[str | None]) -> list[str]:
    ...
```

### 5.1 执行顺序

1. 保存原始输入。空昵称进入明确的异常或回退分支，不生成虚构分段。
2. 先保护新昵称中仍完整存在的旧槽位词，再使用自定义词典。重叠时优先较长词，相同长度优先旧槽位词，再按旧槽位顺序稳定选择。
3. 剩余部分用 jieba 精确模式分词，初稿关闭 HMM；保留原字符串位置，连续 ASCII 字母数字不从中间切断。
4. 初始保护词为“<昵称段1>”“<昵称段3>”“<昵称段4>”“<昵称段5>”“<昵称段6a>”“<昵称段6b>”。“<昵称段2前缀>”与紧随的 ASCII 字母数字串合并。“<昵称段5>”和“<昵称段6a>”保持分开，不恢复旧稿中的五段拆法。
5. 超过六段时，合并相邻合计长度最短的一对，同长取最左；初稿不允许合并已经完整对应旧槽位的保护词。若所有可选对都破坏旧槽位，则返回 needs_review，而不是强行挤成六段。新成员无旧槽位时对所有相邻对计算。长度按 Unicode 字素簇计算。
6. 校验所有片段非空、数量不超过六、拼接结果与完整输入完全相同。

英文、数字、表情和空格不能在处理时被随意删除。自定义词典负责减少错误切分，最短相邻合并仅负责限制段数，不能保证语义始终正确。保留前端人工调整分段的入口。

### 5.2 目标样例

```text
输入：<昵称段1><昵称段2a><昵称段3><昵称段4><昵称段5><昵称段6a>

输出：
[
    "<昵称段1>",
    "<昵称段2a>",
    "<昵称段3>",
    "<昵称段4>",
    "<昵称段5>",
    "<昵称段6a>"
]
```

该输出是算法的验收样例，不是已经运行得到的结果。示例中的昵称已替换为占位符，真实样本不进入公开仓库。需要词典及合并规则配合，不能假设原生 jieba 会直接给出这些片段。

## 6. 现有 Excel 与写入规则

以本目录下 `输出示例/鸿爪录.xlsx` 为参考工作簿；该文件含真实成员昵称，只保留在本地，不进入公开仓库。已读取的工作表为 `<工作表1>`、`<工作表2>`、`<工作表3>`、`<工作表4>` 和 `注释`，没有合并单元格。实际运行时应通过配置指定工作簿路径；开发验证先使用副本，保留参考文件。

### 6.1 成员工作表

| 列 | 现有内容 | 新记录写入规则 |
|---|---|---|
| A | 日期，表头为空 | 本次记录日期 |
| B | 元谥 | slots[0] |
| C | 亨谥 | slots[1] |
| D | 利谥 | slots[2] |
| E | 贞谥 | slots[3] |
| F | 常谥 | slots[4] |
| G | 平谥 | slots[5] |
| H | 备注 | 与上一条记录相比的槽位变化 |

首次按顺序填槽；后续直接使用 align_slots 的六槽结果，允许中间留空，写表函数不得重新移动槽位或重新分词。

上面的六段样例依次写入 B～G。删除<昵称段3>后 D 留空，E、F、G 保留对应位置。完整旧新昵称单独保存，历史 Excel 行不修改。

用数据库中的用户 ID 与工作表名映射定位成员，不能根据昵称猜测 `<工作表1>` 等表名。新增成员初稿用用户 ID 作表名；保留旧表名，管理员先绑定身份。有同名表但未绑定时报告冲突，不覆盖。新表复制参考表表头、列宽和数据行样式，不复制历史。

工作簿存在带格式的空行，必须查找最后一条实际记录，不能简单使用最大行号追加。检查时各表最后有内容的行为：`<工作表1>` 第 3 行、`<工作表2>` 第 7 行、`<工作表3>` 第 5 行、`<工作表4>` 第 4 行；这些是样本状态，代码不得硬编码。部分表头含制表符，匹配表头时去除首尾空白，不改动历史单元格内容。

### 6.2 注释工作表

每次变更同时追加一行：

| A：修改时间 | B：成员 | C：变迁 | D：修改记录 |
|---|---|---|---|
| 记录时间 | 配置的成员显示名称 | 完整旧昵称 → 完整新昵称 | 各槽位变化说明 |

只有发现时间时，系统及文档应明确其含义。历史表内既有日期与记录原样保留。

### 6.3 写入函数原理

`write_in_excel.py` 接收工作簿路径、成员工作表映射和本次已保存的变更记录，返回保存后的原工作簿路径。

1. 加载现有工作簿，检查目标成员表和注释表结构。
2. 定位实际末行，在下一条记录位置写入。
3. 复制相邻有效记录的字体、边框、填充、对齐方式、日期格式与行高，不复制旧数据。
4. 写入成员表和注释表；用户提供的昵称按文字写入，不作为 Excel 公式执行。
5. 保存到同目录临时文件，验证可打开及两处记录完整后替换原文件。
6. 返回原路径，供上传使用。

保存失败时保留原文件，并报告任务失败。业务队列串行运行，无需为两个业务写表任务再设计并行锁；若文件被 Excel 等外部程序占用，正常报告并等待重试。

数据库初稿如下，队列状态和外部发送复用 Main 的 tasks/outbox：

| 数据类别 | 所需内容 |
|---|---|
| members | `(group_id,user_id)` 主键；latest_observed_nickname、latest_observation_seq、last_exported_event_id、current_slots JSONB、display_name_override、sheet_name、observed_at |
| nickname_events | id UUID；task_id 唯一；group_id、user_id、observation_seq、old/new_nickname、old/new_slots JSONB、observed_at、segmentation_version、alignment_version、status、reason、备注 |

- 重试同一任务时，复用同一个变更 ID，不创建第二条改名记录。
- 初稿在隐藏技术表 `_cuo_export` 记录 event_id、user_id、成员行号、注释行号、new_nickname 哈希，与两处业务记录一起保存。重试发现同 event_id 同哈希则直接返回原路径；哈希冲突报告错误。
- 已导出但尚未上传时，只重试上传，不再追加 Excel 行。
- 已上传但预制消息未发送时，只处理消息步骤。
- 上传超时但是否成功不明确时，先核查可用回执或群文件状态，避免盲目重复上传。
- 失败任务记录状态后释放队列，不无限阻塞后续任务。

1. **NapCat 采样**：验证群号、用户 ID、昵称字段、昵称观察途径及上传能力，保存真实测试样例。
2. **成员映射与基线**：关联现有四个工作表与真实用户 ID，确认首次观察及新增成员处理规则。
3. **分词模块**：实现保护词典、jieba 分词、规则合并和六段上限。验证目标昵称、英文数字、表情、超长分段以及原文可还原。
4. **Excel 模块**：在工作簿副本上验证两表追加、格式空行处理、少于六段清空尾部和历史内容不变，同时编写 `write_in_excel.md`。
5. **数据库与队列**：确定表结构、任务状态及幂等标记，验证同一任务重复执行不会重复追加记录。
6. **主流程与 QQ 联调**：接入 Main，完成分词、写库、写表、上传、发送及失败重试。

关键验收场景：新旧昵称相同不新增；首次观察不伪造变更；指定昵称拆分符合样例；两个人连续改名按队列顺序完成；文件被占用时原文件不损坏；导出后重试不重复加行；上传失败不发送成功文案。

## 11. 槽位对齐算法初稿

### 11.1 标准 IO

`align_slots(old_slots, new_parts)`：old_slots 固定长度为 6，空位为 null；new_parts 为新昵称顺序分段。返回 status、slots、changes、reason。status 为 aligned 或 needs_review。自动对齐不使用 AI。

### 11.2 相似度

采用 Levenshtein 编辑距离，插入、删除、替换代价均为 1，比较单位为 Unicode 字素簇。

```text
similarity = 1 - distance / max(len(old), len(new))
```

相同值为 exact；初稿 similarity ≥ 0.60 才允许视作修改。低于阈值只按删除加新增处理，不声称语义相同。

### 11.3 有序动态规划

状态是“已处理旧槽位数、已消费新片段数”。遍历六个旧槽位，每个槽位可以：

| 动作 | 条件 | 代价 |
|---|---|---|
| keep | 旧值与下一新片段相同 | 0 |
| modify | 非空旧值与下一新片段相似度 ≥ 0.60 | 1-similarity |
| delete | 非空旧值消失，新槽留空 | 0.65 |
| leave_empty | 原空槽继续空着 | 0 |
| insert | 新片段进入原空槽 | 0.65 |
| replace | 不相似新片段替换旧值，等于删除加新增 | 1.30 |

keep/modify/insert/replace 消费一个新片段，其余动作不消费。结束必须恰好遍历六槽且用完所有新片段，不能丢字、重排或重复占用片段。

候选按以下优先级排序：完整旧片段保留数量最多；总代价最低；modify 次数最少；新片段占用槽位序列字典序最小。保留最优与次优两个不同槽位分配。

自动通过需同时满足：所有可完整保留的旧片段均为 keep（重复词按实际出现次数计）；在相同完整匹配数量下，最优与次优代价差至少 0.15。只有一个候选时跳过差值检查。不满足则 needs_review，禁止静默改用从左到右重新填槽。

完整旧词换序导致不能同时保留、插入位置没有空槽、近似匹配冲突，都进入人工修正。保存候选供管理端选择；人工选择也必须满足六槽及按序拼接等于新昵称。


| 槽位 | 旧值 | 新值 |
|---|---|---|
| 元谥 | <昵称段1> | <昵称段1> |
| 亨谥 | <昵称段2a> | <昵称段2b> |
| 利谥 | <昵称段3> | null |
| 贞谥 | <昵称段4> | <昵称段4> |
| 常谥 | <昵称段5> | <昵称段5> |
| 平谥 | <昵称段6a> | <昵称段6b> |

## 13. 验收矩阵

| 场景 | 期望 |
|---|---|
| 初次观察新成员 | 备注“初创”，无改名通知 |
| 同一成员同一昵称再次观察 | 不加行、不通知 |
| 本文六段初始昵称 | <昵称段5>和<昵称段6a>分别在常谥、平谥 |
| <昵称段2a> 改 <昵称段2b> 并删除<昵称段3> | 亨谥更新、利谥空，贞/常/平谥不前移 |
| 空利谥位置恢复<昵称段3> | 填回利谥 |
| 两个完整旧词换序 | needs_review，不静默重排旧对应 |
| 两锚点间新增词但没有空槽 | needs_review，不挤占锚点 |
| 同 event_id 重试写表 | 两张业务表都不重复追加 |
| 导出失败 | 原文件可读、数据库保留新观察、状态为失败 |
| 上传成功但通知失败 | 只重试通知，不再上传 |

阈值 0.60、候选差值 0.15、成员同步周期及人工处理入口属于下一轮讨论重点。本稿给出确定性算法供评审，不把“合理匹配”作为执行者自行发挥的要求。
