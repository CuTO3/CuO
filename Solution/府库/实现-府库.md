# 府库

## 1. 模块综述

府库负责氧化铜的数据管理：保存聊天消息、成员当前信息、任务执行日志、总结历史和卜算记录，并提供查询、更新与事务接口。

本文件记录已确定的数据组织与执行关系，尚未创建数据库或业务代码。此前各模块初稿中的 tasks、outbox、nickname_events、summary_versions、divine_records、fortune_accounts、fortune_ledger、day_archives 等独立表方案，由本文的五表方案替代，不同时实现两套结构。

## 2. 数据库结构

```text
database：CuO
└── schema：<group_id>
    ├── log
    ├── messages
    ├── members
    ├── summaries
    └── divinations
```

- 数据库对应机器人；schema 对应群。以后加入其他群，建立相同结构的独立 schema。
- 群内表不重复保存 group_id。Main 从可信事件取得群号，府库选择对应 schema。
- 纯数字 schema 在 SQL 中使用双引号，如 `"<group_id>".messages`。数据库名称保留 `CuO` 的大小写；创建时按带引号标识符处理。
- schema 必须从已登记的群配置中选择，不能把用户消息或 AI 输出拼接成 SQL 标识符。业务字段使用参数化查询。
- 代码目录使用 `database/`，供 receiver、Main 和各功能模块调用，不作为一种可由用户触发的 opt。

## 3. 标准 IO 

调用府库时传入 group_id 以及该操作需要的标识和数据。府库负责选择 schema、校验记录关联、提交或回滚，不调用 DS、不发送 QQ 消息。

| 调用方 | 府库提供的操作 |
|---|---|
| receiver.py | 保存消息、查询成员、建立任务日志 |
| Main.py | 取待处理任务、记录阶段、保存发送动作及回执 |
| conversation | 读取本群聊天与已保存回复 |
| memento | 查询旧昵称与槽位、保存改名历史、更新成员当前状态 |
| summary | 读取聊天素材、保存和查询总结版本 |
| divine | 检测当日卜算、恢复草稿、结算福缘 |

业务模块返回结果或动作给 Main；府库不决定先执行哪个业务。以下字段是讨论确定内容的结构化整理，具体索引与迁移脚本在实现时围绕这些约束编写。

## 4. 接口

保留统一读写入口 `PGsql_write`、`PGsql_read`。下面补齐接口初稿：记录采用带字段名的字典，多条记录组成列表，不依赖字段的位置；参数名使用 records，不用 list 覆盖 Python 内置类型。

```python
async def PGsql_write(table: str, records: list[dict], *, group_id: str,
                      mode: str = "insert", key_fields: tuple = (), transaction=None) -> list[dict]:
    ...

async def PGsql_read(table: str, *, group_id: str, filters: dict,
                     order_by: tuple = (), limit: int | None = None,
                     transaction=None) -> list[dict]:
    ...
```

### 4.1 写入

table 只允许 log、messages、members、summaries、divinations。records 每项是一条包含字段名的记录。返回数据库写入后的完整记录列表，包含生成的主键；不能只返回 True。

- insert：插入；唯一键冲突报明确异常，不静默覆盖。
- update：按 key_fields 定位记录，仅修改本次明确传入的非键字段；key_fields 不得为空，缺键或匹配不到记录均报错。
- upsert：必须指定与表唯一约束一致的 key_fields；存在则只更新明确传入字段，否则插入。不能用它绕过卜算结算流程重复更新福缘。
- records=[] 返回 []，不执行 SQL。传入非白名单表、未知字段或非法类型，在访问数据库前拒绝。

```python
rows = await PGsql_write(
    table="members",
    records=[{"user_id": "<user_id>", "display_name": "<display_name>"}],
    group_id="<group_id>",
    mode="update",
    key_fields=("user_id",),)
```

### 4.2 读取

读取返回完整记录组成的 list；单条也是 `[record]`，没有结果为 `[]`。SQL 错误应抛出异常，不能伪装成查无记录。

```python
rows = await PGsql_read(
    table="divinations",
    group_id="<group_id>",
    filters={"user_id": "<user_id>", "business_date": "2026-10-25"},
    limit=1,)
```

filters 字段之间为 AND；普通值为相等，None 为 IS NULL。时间范围使用结构化条件，例如 `{"sent_at": {"gte": start_at, "lt": end_at}}`。初稿允许 eq、gte、gt、lte、lt、in，禁止传入原始 SQL 字符串。order_by 使用 `(字段名, asc或desc)` 项组成的元组，字段必须在表定义中；limit 为正整数或 None。

### 4.3 事务与缓存边界

不传 transaction 时，写入函数自行开启并提交一个事务；传入时复用调用方事务，不自行提交。多个表一起更新时使用同一事务，例如 divinations、members 和 log 的结算。

`PGsql_read` 始终直接读 PG，保持名称和行为一致；业务日常读取使用下文缓存入口，命中则不调用它。事务内读取、领取任务、结算检查始终走 PG，不依赖文件判断。

写入事务提交后才更新文件缓存；回滚不更新缓存。事务内积累受影响的日期和文件，提交后统一刷新。缓存写失败标记失效并记录修复任务，不把“PG 已提交”误报成“业务未执行”，也不重新加分。

## 5. log：任务执行与历史

每个请求或系统任务占一行。log 是可恢复的任务日志，同时保留改名历史等业务数据，不能按普通调试日志定期清空。

| 字段 | 类型 | 内容 |
|---|---|---|
| task_id | UUID，主键 | 任务唯一编号，重试保持不变 |
| created_at | TIMESTAMPTZ | 接收并建立任务的时间 |
| triggered_at | TIMESTAMPTZ | 原请求或观察事件时间，排队后不改变 |
| business_date | DATE | 按 04:00 划分的所属日期 |
| request_type | TEXT | message、conversation、summary、memento、divine 或系统任务类型 |
| user_id | TEXT，可空 | 请求者或被观察成员；系统任务可为空 |
| message_id | TEXT，可空 | 关联原消息；系统事件可能没有消息 ID |
| original_text | TEXT，可空 | 触发请求的原文字 |
| params | JSONB | 识别出的参数或系统事件内容 |
| status | TEXT | pending、running、completed、failed、needs_review |
| business_status | TEXT | pending、running、completed、failed |
| step | TEXT | 当前或失败步骤 |
| result | JSONB | 已保存的业务结果关联、改名历史、发送动作与动作状态 |
| error | JSONB，可空 | 错误码、步骤和原因 |
| completed_at | TIMESTAMPTZ，可空 | 全部要求完成的时间 |

入库时普通消息任务尚未识别意图，request_type=message；intention 返回后更新为具体功能，params 同时保存。改名和定时任务直接写对应类型。

任务状态路径为 pending → running → completed；失败进入 failed，发送结果不明确进入 needs_review。business_status=completed 但 status=failed 时，表示业务已完成而发送等后续步骤失败，禁止重新执行业务。

result 的内容按类型区分：

| 类型 | 保存内容 |
|---|---|
| conversation | 生成的回复及发送动作 |
| memento | 完整旧新昵称、旧新六槽、备注、文件信息、发送动作 |
| summary | summary_id 及发送动作，正文以 summaries 为准 |
| divine | divination_id 及发送动作，结算结果以 divinations 为准 |
| archive_day | 归档业务日期、范围、记录数、JSON 快照或快照引用及版本 |

发送动作保存于 result.actions，按数组顺序执行，每项记录稳定 action_id、type、payload、status、receipt、error。动作状态为 pending、sending、sent、failed、unknown。生成动作后先写日志，再调用 NapCat；成功回执也必须写日志。

明确 sent 的动作不重复执行；失败恢复只执行尚未完成且确认可重试的步骤。发送超时后无法判断是否成功时标为 unknown，不自动假设失败。

同一消息同时触发改名与 @ 请求时，messages 只存一条，log 建两条，先改名、后请求。它们关联同一 message_id，但 task_id 不同；不能给 log.message_id 单独加唯一约束。

## 6. messages：原始聊天消息

所有接收到的群消息均保存，不限于 @ 机器人的请求。每条原消息占一行。

| 字段 | 类型 | 内容 |
|---|---|---|
| id | BIGINT，主键 | 内部记录序号，供排序和快照界限使用 |
| message_id | TEXT | NapCat 消息标识 |
| sent_at | TIMESTAMPTZ | 原消息发送时间 |
| received_at | TIMESTAMPTZ | 服务接收时间 |
| business_date | DATE | 消息所属业务日期 |
| user_id | TEXT | 发言者 QQ 号 |
| nickname | TEXT | 发言时的完整群昵称快照 |
| text | TEXT | 提取出的正文 |
| segments | JSONB | 原始文字、图片、@、回复等消息段，不覆盖 |
| generated_by | TEXT，可空 | 本机器人生成来源，如 divine、summary；成员消息为空 |
| processing | JSONB | 标准化版本、图片哈希、缓存描述、处理状态等派生数据 |

processing 是容纳已讨论图片文字缓存的字段，不增加独立缓存表。相同内容图片可通过哈希查询已有处理结果复用；原始 segments 保留。图片识别或标准化失败不影响原消息已经保存。

消息去重依赖真实 NapCat 消息标识；当前单机器人、单群 schema 内按 message_id 去重。接入多个机器人账号时再补 self_id 形成组合约束，不能假定跨账号消息标识一定相同。

## 7. members：成员当前状态

每个成员一行，user_id 是稳定主键。昵称变化不能新建成另一个人。

| 字段 | 类型 | 内容 |
|---|---|---|
| user_id | TEXT，主键 | 用户 QQ 号 |
| nickname | TEXT | 当前完整群昵称 |
| display_name | TEXT，可空 | 前端手动设置的显示名 |
| slots | JSONB | 六个槽位组成的数组，空槽为 null |
| sheet_name | TEXT，可空 | 鸿爪录工作表名称 |
| fortune | BIGINT，默认0 | 当前累计福缘 |
| updated_at | TIMESTAMPTZ | 最近更新时间 |

显示名称优先 display_name；未配置时取 nickname 前四个字。自动改名不覆盖 display_name。六槽对应元谥、亨谥、利谥、贞谥、常谥、平谥，保留中间空槽。

改名历史放 log.result，不在 members 内无限追加历史数组。新名字已观察到但尚未成功对齐时，nickname 可以更新，slots 暂保留上次确认值；对应 pending/failed 的 memento 日志说明这两者尚未同步，不把旧槽位冒充新昵称的拆分。

当日是否卜算通过 divinations 检查，不放每日清零的布尔字段。修改 nickname、slots 时只更新相应字段，不整行覆盖 fortune，避免与结算互相覆盖。

## 8. summaries：总结历史

每次成功生成保存一行，同一天允许多份，不覆盖旧结果。

| 字段 | 类型 | 内容 |
|---|---|---|
| id | UUID，主键 | 总结记录编号 |
| task_id | UUID，唯一，关联 log | 防止同任务重试重复保存 |
| business_date | DATE | 总结所属业务日期 |
| start_at | TIMESTAMPTZ | 实际覆盖起点 |
| end_at | TIMESTAMPTZ | 实际覆盖终点 |
| content | TEXT | 总结正文 |
| created_at | TIMESTAMPTZ | 生成时间 |

按日期查询时，先按 end_at 降序，再按 created_at 降序取一份。只有部分覆盖必须在输出中说明，不把中午生成的总结描述为全日记录。

提示词版本、输入消息快照、来源引用等初稿元信息先保存在关联 log.result，正文只有 summaries.content 一份权威存储。主题总结只在相同主题范围内比较版本，主题范围同样由关联日志保存，避免把“大龙玉专题”当成整日回顾。

写入 summaries 与将 log.business_status 标为 completed、保存 summary_id，在同一事务中完成；发送状态另行更新。

## 9. divinations：卜算记录

同一个成员、同一个业务日期最多一行；草稿、失败恢复和最终结算使用同一记录。

| 字段 | 类型 | 内容 |
|---|---|---|
| id | UUID，主键 | 卜算记录编号 |
| task_id | UUID，唯一，关联 log | 最初建立该记录的任务 |
| user_id | TEXT | 卜算用户 |
| business_date | DATE | 卜算所属业务日期 |
| status | TEXT | generating、settled、failed |
| zhou_yi | JSONB | 六爻、本卦、动爻、变卦 |
| tarot | JSONB | 卡牌及正逆位 |
| dictum | JSONB | 原文及出处 |
| keyword | TEXT，可空 | 今日应事关键词 |
| advice | TEXT，可空 | AI 短解读 |
| luck_delta | INTEGER | 本次卦运，-10～+10 |
| fortune_before | BIGINT，可空 | 结算前福缘 |
| fortune_after | BIGINT，可空 | 结算后福缘 |
| content | TEXT，可空 | 完整消息正文 |
| created_at | TIMESTAMPTZ | 创建时间 |
| settled_at | TIMESTAMPTZ，可空 | 结算完成时间 |

约束：`UNIQUE(user_id,business_date)`；settled 时 before/after 非空且 after=before+luck_delta。随机结果在草稿阶段保存，恢复不能重抽。尚未生成的草稿字段允许为空，完成结算时必须校验齐全。

当天已有 settled 时提示已占卜；generating 或 failed 的记录进入原任务恢复流程，不另抽一卦。若用新请求恢复旧记录，新 log 关联同一 divination_id，不修改其原始 task_id。

### 福缘结算事务

```text
BEGIN
→ 锁定本次 divinations，检查是否已 settled
→ 锁定该用户 members，取得当前 fortune
→ 计算 fortune_before、luck_delta、fortune_after
→ 保存 divinations 全部结果并标记 settled
→ 更新 members.fortune
→ 更新 log 的业务完成状态及结果关联
COMMIT
```

已 settled 则返回原记录，不再加分。失败全部回滚；发送发生在事务提交之后。无需另建 fortune_accounts 或 fortune_ledger：members 保存余额，divinations 保存每次卜算的前后值。

## 10. 日期规则

business_date 一律为 PostgreSQL DATE，只含年月日，例如 2026-10-25；不是含时间的字符串。

统一采用北京时间 `[当天04:00,次日04:00)`。例如 2026-10-25 02:00 的 business_date 为 2026-10-24；04:00 整开始新的日期。计算依据原触发时间，不能改用队列执行完成时间。

sent_at、received_at、triggered_at、created_at、updated_at、start_at、end_at、settled_at、completed_at 等保存为 TIMESTAMPTZ，展示时转换为北京时间。

## 11. 接收、执行与统一发送

```text
receiver.py（与 Main.py 同级）
→ 保存 messages
→ 观察昵称并建立需要的 log
→ 继续接收下一条消息

Main.py
→ 读取 pending 日志并标记 running
→ message 调用 intention，系统任务直接分发
→ 调用对应业务模块
→ 保存结果及发送动作
→ 调用消息发送子函数
→ 按动作回执更新日志
→ 全部完成后标记 completed
```

业务仍串行，接收与入库持续进行。memento 不再自行调用 NapCat；上传文件和预制消息都作为动作返回，由 Main 调用统一发送子函数按顺序执行。

鸿爪录动作顺序固定为 upload_file → send_message；上传失败停止后续成功通知。重试不能因原工作簿已被后续任务修改而上传错误版本，待发送文件信息需包含内容哈希及可恢复的版本引用。

## 13. 本地缓存与代码目录

> 路径更新：依据同级.infrastructure及用户最新要求，以Main文档2.1节为准。下文旧代码根data目录不再作为目标路径：messages.jsonl移到Function/summary/cache/{群}/{日期}/，divined_users.json与keywords.json移到Function/divine/cache/{群}/{日期}/，current.json与manifest移到database/cache对应群和日期。PG、运行鸿爪录、待发送快照等永久数据与代码分离；初始化仍由府库统一管理，不能直接删除整个功能目录。后文读取、初始化和恢复规则继续有效，只替换物理路径。

PG 保存完整历史，代码根目录下的 data/ 保存近期运行缓存。五张表不变，不因缓存增加数据表。缓存由府库统一管理，各业务模块不直接读写文件。

```text
Main.py
receiver.py
database/
├── database.py          PGsql_write、PGsql_read 与事务管理
├── cache.py             缓存读取、提交后更新、失效与重建
└── initialize.py        initialize_day
data/
└── <group_id>/
    ├── current.json
    └── 2026-10-25/
        ├── manifest.json
        ├── messages.jsonl
        ├── divined_users.json
        └── keywords.json
```

目录中的日期是业务日期，不是文件写入日期；缓存文件使用 UTF-8。运行数据不提交到源码版本库，不放入网页可直接下载的静态目录。

| 文件 | 内容及权威来源 |
|---|---|
| current.json | 当前已完成初始化的业务日期和初始化任务 ID；只作定位提示 |
| manifest.json | 日期、格式版本、各缓存 ready/dirty 状态、生成时间及初始化版本 |
| messages.jsonl | 该业务日完整消息记录，每行一条；来自 messages，含 processing |
| divined_users.json | 已成功结算的 user_id → divination_id；来自 status=settled 的 divinations |
| keywords.json | 今日应词候选、关联用户、来源消息、摘录、规则版本；副本保存在初始化日志 |

文件不存在、格式损坏、版本不符或被标为 dirty 时，从 PG 重建；不能把损坏文件当成空数据。程序启动先校验或重建缓存再对业务开放，即使文件看似完整也不直接信任上次异常退出留下的状态。

### 13.1 读写顺序

```text
写入：PG 事务成功提交 → 更新相关缓存 → 缓存失败则失效、安排修复
读取：按任务业务日期定位 → 有效缓存 → 未命中/失效则读 PG 并重建
```

领取 log 任务和福缘结算仍直接访问 PG。divined_users 可快速回答“已经完成”；未命中时仍检查 PG，区分未占卜、生成中和失败草稿。不能因为本地集合为空就跳过唯一约束。

messages.jsonl 以数据库 id 去重；新消息提交后追加。processing 更新需要替换该日缓存快照，不能在旧行后追加同一消息的第二个版本。重建先写临时文件，验证后原子替换，禁止边读边清空原文件。

接收线程与业务 worker 都通过同一府库缓存管理器操作，按群串行写缓存。重建期间仍允许消息提交 PG；受影响缓存保持 dirty，待缓存管理器在写入方同步点补齐提交结果后才标 ready。不能仅用 MAX(id) 认定覆盖完整，因为事务提交顺序不必与编号一致。初稿用群级短锁保护“PG 提交到缓存更新”和最终重建切换；锁内不调用 AI、NapCat或进行大批历史运算。

### 13.2 今日应词

今日业务日期为 D 时，应词从 D-1 的聊天提取；优先使用周易文档中的本地关键词规则，不在初始化时为每条消息调用 AI。

每个候选至少保存 keyword、user_ids、message_ids、source_business_date、source_excerpts、scope（personal/group）、score。用户范围不明确的候选不能描述成请求者亲历。

keywords.json 顶层保存 business_date、source_business_date、rule_version、generated_at、items。同样内容写入 log 中 initialize_day 任务的 result.keywords，形成 PG 副本；历史输入仍在 messages。

无昨日消息时 items=[] 并标记 source_status=no_data。提取错误为 failed，不冒充无数据；初始化失败时周易可从 PG 读取同日期已成功版本，否则使用无素材兜底，不能拿前一天应词冒充今天。

## 14. 每日 04:00 初始化

Main 在北京时间04:00建立 initialize_day 系统任务，调用 `database/initialize.py`：

```python
async def initialize_day(group_id: str, business_date: date, task_id: str) -> dict:
    ...
```

返回 business_date、status、keyword_count、message_count、divined_count。business_date 显式传入，执行时不能再次用系统时间改成另一天。相同群、日期的初始化由串行 Main 查日志复用任务，启动补跑也遵守同一规则。

### 14.1 执行流程

```text
确定目标新业务日期 D，保存初始化任务日志
→ 确认昨日接收数据已经写入 PG，检查旧日归档状态
→ 需要时补建昨日 archive_day 任务（不发群消息）
→ 从昨日聊天生成今日应词，保存 PG 副本
→ 从 PG 查询 D 当天已有消息，建立 messages 缓存
→ 从 PG 查询 D 当天 settled 卜算，建立 divined_users 缓存
→ 写 keywords 与 manifest，校验日期和记录完整性
→ 在缓存写入同步点补齐期间提交的数据，原子切换 current.json
→ 标记初始化 completed
→ 按清理规则处理旧日临时缓存
```

这里“清空今日消息、是否占卜记录”表示进入新的日期分区，不删除 PG，也不直接把正在使用的旧文件清零。正常04:00刚到时，新日缓存可能为空；若排队到04:10或停机到05:00才执行，就必须载入新日已经存在的记录。

初始化等待执行时，receiver 按消息实际 business_date 入库，并通过缓存管理器建立或更新对应日期文件，不等待 current.json 更新。业务任务也按自身日期访问，不能全部依赖 current.json 路径。

### 14.2 重复运行与失败恢复

- 当天已成功初始化且缓存有效：直接返回现有状态，不清空、不重复抽取关键词。
- 缓存丢失：从 PG 重建；应词优先恢复同日成功初始化日志的副本。
- PG写入成功、文件替换前中断：按日志恢复缓存，不重做业务或删除已有结算。
- 新缓存未完整就绪：保留旧 current.json，新日读取按显式日期走 PG；不得假装初始化成功。
- 重启发现跨过04:00：补跑当前业务日初始化，历史归档按缺失日期另补；不需要为停机期间每一天都建立临时缓存。
- 迟到消息按原业务日期入库。已生成应词的来源范围有更新时标记该初始化日志 source_dirty；下一次使用前可在队列内生成新版本，已经保存的卜算不重写。

### 14.3 清理范围

只清理 data/{group_id}/{业务日期} 下可重建的缓存。初稿保留当前日和上一日；更早日期在确认 PG 数据存在、无未完成任务引用后清理。迟到的旧日请求可直接查 PG，不必永久保留文件。

不清理成员累计福缘、昵称历史、旧总结、卜算记录、任务日志、intention.json、鸿爪录.xlsx 或尚待上传的文件快照。运行时不得以整个代码目录作为清理目标。

## 15. 验收要点

1. 同一消息重复上报不会重复保存和执行；改名加 @ 则是一条消息、两条不同任务。
2. 重启能查询未完成日志；业务已完成只恢复发送，不重新调用模型、写 Excel 或结算。
3. 同日多次总结均可保留，按覆盖时间和生成时间选版本。
4. 卜算同用户同日唯一；事务失败不产生“已加福缘但没有卜算记录”。
5. 03:59:59 与 04:00 的业务日期不同，排队跨日不改日期。
6. 群 schema 隔离，群 A 的查询不能返回群 B 的消息、成员或结果。
7. 图像文字缓存不覆盖原始 segments；手动显示名不被自动改名覆盖。
8. 五张表承担的业务历史都保留，不能把 log 当作可随意清空的调试文件。
9. PGsql_read 单条返回列表、无数据返回空列表、异常不伪装成空列表；update 未传定位键时拒绝执行。
10. 同一事务更新多个表，提交前不更新缓存，回滚后缓存保持原值。
11. 04:00 切换只建立新日缓存，旧日任务仍能按原日期完成，福缘累计值不清零。
12. 05:00 补初始化时已存在的新日消息和已卜算用户完整恢复；重复运行不让用户重新占卜。
13. 接收消息与重建缓存交错时，切换后的缓存不丢记录、不重复；有疑问时保持 dirty 并读 PG。
14. 今日应词有用户和消息来源；错误、无数据、缓存缺失三个状态分别处理。
