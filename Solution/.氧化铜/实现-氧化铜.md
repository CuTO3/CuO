# 氧化铜 Main 设计实现路径

## 1. 模块综述

本稿先补齐可讨论的完整实现方案，不代表已实现或通过 NapCat 联调。标记为“已定”的内容来自当前讨论；标记为“初稿方案”的内容已经给出具体处理方式，后续逐项讨论后再冻结，执行者不自行更换。

已定：Python、FastAPI、PostgreSQL、HTML 管理网页；群消息持续接收和保存；业务任务逐个排队执行；四个功能为 conversation、memento、summary、divine；一天统一为北京时间 04:00 至次日 04:00。大千录不在本期。

本文负责入口、排队、分发、数据库边界、定时归档和结果发送。意图识别详情见本目录 `意图识别/实现-意图识别.md`，众声录和鸿爪录见各自实现文档。

数据管理已独立命名为“府库”，详见 `../府库/实现-府库.md`。采用 CuO 数据库、群号 schema、log/messages/members/summaries/divinations 五张表。此前初稿的独立 tasks/outbox 等表不再建立；任务状态和发送回执保存于 log。

Main 编排流程，不内嵌分词、模型提示词、Excel 操作和 SQL。Infrastructure 封装共享能力；Function 保存业务模块。业务模块通过普通 Python 导入和函数调用执行，不为每条消息启动新 Python 进程。

开发时启用一个业务 worker；管理端不直接改 JSON、Excel 或运行中的业务状态，而是提交修改任务到同一队列。接收服务允许持续入库，不视为并行执行业务功能。

### 2.1 按同级 .infrastructure 约定划分完整目录

本节依据项目同级 `../../../.infrastructure/README.md` 的服务器布局，区分软件、代码环境、服务、永久数据与功能缓存。它不是后端 Python 的 `Infrastructure/` 目录：前者是运维约定，后者只是共享代码包。

以下均为规划，不代表目录或软件已经创建、安装或部署。本地继续保留 Requirement、Solution、Workplace；后端代码规划放 Workplace/backend，前端只保留 Workplace/frontend 位置，不在本次展开页面或前端服务实现。

### 2.2 Infrastructure 与府库的职责边界

| 文件 | 负责 | 不负责 |
|---|---|---|
| task_queue.py | 从府库log领取可执行任务、按序调度、恢复阶段 | 不另建任务表，不复制业务算法 |
| onebot_client.py | 连接、请求编码、echo与Future映射、断线和超时通知 | 不决定发什么，不自行重发结果不明的消息 |
| model_client.py | 调用配置的模型接口、返回模型文本和用量 | 不维护各业务提示词，不把模型输出直接当命令执行 |
| archive.py | 查询已结束日的数据、组织归档内容、保存archive_day日志 | 不清空PG历史，不生成群总结或主动发消息 |
| clock.py | 统一计算时区、业务日期、半开时间范围 | 不在每个模块重复实现日期判断 |
| database/database.py | PG连接、白名单表读写、事务 | 不调度任务、不直接访问NapCat |
| database/cache.py | 运行缓存读写、失效和重建 | 不成为另一套权威数据库 |
| database/initialize.py | 刷新今日应词、建立新日缓存、恢复当天已有状态 | 不清零累计福缘、不删除历史卜算 |

归档与初始化分开：archive.py 处理“上一日历史留存”，initialize.py 处理“新一日运行数据”。Main 的定时逻辑建立相应任务；初始化如发现归档缺失，只请求补建任务，不自行启动第二个worker。两者均调用clock.py和府库，不能各自写一套SQL或日界规则。

### 2.3 主要调用关系

```text
NapCat事件 → receiver → 府库messages/members/log → 提交后更新缓存
Main → task_queue → 府库log → intention → 对应Function模块
Function模块 → 府库读取数据、保存业务结果 → 返回actions给Main
Main → send_message → onebot_client → NapCat
NapCat回执 → receiver分流 → onebot_client唤醒等待者 → Main写动作日志
Main定时任务 → initialize / archive → clock + 府库
AI业务模块 → model_client → 模型服务
管理网页 → 认证后的管理接口 → 查询府库或提交修改任务
```

发送回执走网络层即时分流，不排在业务队列后；否则Main等待回执时会阻塞自己。接收与入库不等待DS完成，业务功能仍一次执行一个。

### 2.4 文件保留与清理

- Requirement、Solution 是文档与参考资料；本次仅补目录设计，不把它们移动到代码目录。
- Function/divine/data 是静态卦辞、映射、概率资料；运行缓存分布在各功能同级cache目录，永久数据位于独立数据区，不再使用代码根data统一存储。

- intention.json 按用户约定仍位于intention_resources，运行新增语料不随日初始化清空；同步到PG时使用log中的系统记录，不增加第六张表。
- 真实密钥由环境或受保护的本地配置提供；.env.example只记录字段名。尚未讨论的长期记忆存储不擅自增加表或目录实现。

## 3. 标准 IO

Main 接收适配后的请求对象：

| 字段 | 类型 | 规则 |
|---|---|---|
| task_id | UUID 字符串 | 每个持久化任务唯一，重试不改变 |
| group_id | 字符串 | 来自事件，按群选择数据及文件 |
| user_id | 字符串或 null | 消息发送者或被观察成员；定时任务为空 |
| message_id | 字符串或 null | 原协议消息标识，不强制转整数 |
| self_id | 字符串 | 当前机器人账号标识 |
| trigger_type | 枚举 | message、nickname_observed、archive_day、media_describe、admin_update |
| triggered_at | 带时区时间 | 原事件时间，缺失则以接收时间代替并记录来源 |
| received_at | 带时区时间 | 服务实际收到的时间 |
| receive_seq | 整数 | 持久化接收序号，用于同时间排序与快照界限 |
| text | 字符串 | 移除指向机器人的 at 段后的消息正文，其他段单独保存 |
| segments | JSON 数组 | 原始 OneBot 消息段 |
| payload | JSON 对象 | 系统事件内容，例如 new_nickname、business_date |

`opt` 和 `params` 不属于消息入口输入；Main 调用 intention 后得到它们。来自消息正文或 AI 的 group_id、user_id、self_id 均不能覆盖事件身份。

## 4. 接收与持久化（初稿方案）

采用 NapCat 到 FastAPI 的反向 WebSocket 适配；连接鉴权和动作回执通过 onebot_client 封装。具体字段、图片 URL 刷新、上传接口须用真实 NapCat 样本验证，协议适配层不凭复制的聊天文本编写。

每条允许群的事件按以下顺序处理：

1. 校验连接身份、事件类型与允许群；记录 received_at。
2. 保留完整 raw_event，生成统一消息记录；业务日期按 triggered_at 减四小时计算。
3. 以 `(self_id, group_id, message_id)` 对普通消息去重。无稳定消息 ID 的通知使用协议事件标识；没有标识时计算规范化事件摘要，并保留摘要规则版本。
4. 一个数据库事务内保存消息、昵称观察信息及应创建的队列任务；事务失败不将事件标记为已接收成功。
5. 消息中真实 at 段包含机器人 ID，且发送者不是机器人自身时，建立 message 任务。非 @ 消息只存档及建立必要的媒体任务。
6. 机器人发送的消息同样保存，标记 generated_by 和 source_task_id；不得因为回显再次生成业务任务。

同一入站事件的任务排序固定为：昵称观察、媒体描述、用户请求。前序已存在的队列任务不被插队。事件接收过程中可以落盘图片字节，但模型识图属于队列任务。

数据库不可用时返回/记录接收失败，不能只放内存并宣称已持久化；断线补回能力必须实测，无补回能力时在归档记录缺失时段。

## 5. 持久化串行队列

使用 PostgreSQL `log` 表作为持久化任务日志，单 worker 逐个执行，不引入 Redis。执行前先保存任务，执行后更新完成状态。同一消息的改名任务排在 @ 请求前，两者独立记录失败。

状态为 pending → running → completed；失败进入 failed，外部发送结果不明确进入 needs_review。business_status 单独记录业务是否完成，step 记录执行步骤，result.actions 记录各发送动作。恢复先检查这些字段，不能全部从头重跑。租约和重试周期仍属后续实现细节，不增加独立任务表。

单 worker 通过数据库锁确保只启动一个消费者。正常任务顺序严格串行；失败任务延期重试时释放队列，不阻塞后续请求。初稿自动重试最多 3 次，间隔 10、30、120 秒；明确参数错误和结果不明的外部发送不自动重试。

“整条任务重试”不得重复进行模块内已经完成的模型生成、写 Excel、福缘结算或已确认发送。按 task_id 恢复保存的阶段。

## 6. Main 分发

message 任务首先调用 intention：

```python
result = await intention.run(
    text=request["text"],
    triggered_at=request["triggered_at"],)

opt = result["opt"]
params = result["params"]

if opt == "summary":
    result = await summary.run(
        group_id=request["group_id"],
        target_date=params["target_date"],
        cutoff_time=request["triggered_at"],
        request_text=request["text"],
        snapshot_seq=request["receive_seq"],
        task_id=request["task_id"],)

elif opt == "divine":
    result = await divine.run(
        group_id=request["group_id"],
        user_id=request["user_id"],
        triggered_at=request["triggered_at"],
        task_id=request["task_id"],)
```

conversation 接收 group_id、user_id、text、task_id；自己的上下文和记忆由 conversation 内部查询。intention 不接收历史上下文。

nickname_observed 任务直接调用：

```python
result = await memento.run(
    group_id=request["group_id"],
    user_id=request["user_id"],
    new_nickname=request["payload"]["new_nickname"],
    observed_at=request["triggered_at"],
    observation_seq=request["receive_seq"],
    task_id=request["task_id"],)
```

系统任务不能由用户提交的 opt 字符串伪装触发；模块映射是代码里的固定白名单，不使用 eval 或动态导入用户指定路径。

## 7. 公共结果与发送归属

统一由 Main 发送，模块返回业务结果与动作列表：

```json
{
  "status": "ok",
  "result_id": "UUID或null",
  "actions": [{"type": "send_message", "text": "待发送文字"}],
  "error_code": null
}
```

status 允许 ok、no_data、skipped、error。所有模块都只返回结果，不直接调用 NapCat。memento 返回 upload_file 和 send_message 两个动作；Main 调用发送子函数，上传成功后才继续通知。不需要回复时 actions=[]。旧稿 reply_text/delivery_owner 接口由 actions 接口替代。

Main 调用发送子函数，子函数通过共享 onebot_client 访问 NapCat。发送前在 log.result.actions 保存稳定动作标识、内容和 pending 状态；取得明确成功回执后保存消息标识及 sent 状态。动作内容持久化后才能实际发送，不另外建立 outbox 表。

连接断开或超时发生在请求发出后，状态标记 unknown；不假设没发出去，不盲目重试。若 NapCat 无法查询验证，管理端人工决定重发。发送失败不回滚已保存的业务结果，更不能重新增加福缘。

长文本初稿每段不超过 1500 个 Unicode 字符，按空行、换行、字符依次选择切分点；有多段时预留 20 字符放 `(1/3)` 标识。逐段发送并保存回执，失败后仅恢复未明确发送的段。实际 QQ 限额需实测调整该配置。

## 8. 04:00 归档

调度器在北京时间 04:00 创建 archive_day 任务，归档刚结束的 `[D 04:00,D+1 04:00)`，不主动生成总结或发群消息。唯一键 `(group_id, business_date, archive_revision)` 防止重复任务。

归档以 archive_day 系统任务保存于 log，result 记录 business_date、coverage_start/end、revision、message_count、raw_snapshot、keywords 和 mentions；不建立 day_archives 表。快照不嵌入图片二进制，媒体处理数据来自 messages.processing。关键词初稿使用本地词典，未提取时记录空数组和状态。

实时 messages 表仍为源数据，归档不删除消息。迟到消息按实际 event_time 归属，标记对应归档 dirty，生成新 revision，不悄悄覆盖旧快照。程序启动补查从首次接入日到已结束业务日的缺失归档；停机期间没有收到的消息不得虚构。

## 9. 数据表与跨模块约束（初稿方案）

公共表使用 PostgreSQL；时间为 timestamptz，ID 使用字符串或 UUID，不用浮点数保存 QQ 号。

| 表 | 主键及关键字段 | 写入责任 |
|---|---|---|
| log | task_id；类型、状态、步骤、参数、结果、动作回执及改名历史 | receiver/Main/业务模块 |
| messages | id；message_id、user_id、时间、昵称、text、segments、processing | receiver/标准化与媒体处理 |
| members | user_id；当前昵称、显示名、槽位、工作表、fortune | memento/divine |
| summaries | id；task_id、业务日期、覆盖时间、正文 | summary |
| divinations | id；user_id/业务日期唯一；卜算内容及福缘结算前后值 | divine |

府库调用带 group_id，由它选择群 schema；表中不重复保存 group_id。字段、类型与事务以府库文档为准。数据库结构通过迁移管理，不在每条消息到来时建表。群配置放后端配置文件，不增加 groups 表。

## 10. 意图语料文件同步与管理端

保留用户在意图识别文档中指定的 `Function/intention/intention_resources/intention.json`，不改回纯数据库方案。初稿文件顶层为 schema_version、revision、examples、entries。固定示例放 examples，运行累积放 entries；调用 DS 只发送 examples，不发送全部 entries。

写入使用临时文件原子替换，由串行业务 worker 完成。先保存文件，再按稳定语料 ID 幂等 upsert 到 PostgreSQL；同步失败记录待同步 revision。启动时核对文件与数据库 revision：文件缺失可从最新完整副本恢复；双方内容冲突不相互覆盖，禁用冲突缓存并在管理端列出，识别仍可调用模型。

意图文档保留的固定整句规则先匹配，其后查 intention.json，最后调用 DS。`D日/D号` 初稿按当前业务日期的年、月补全，不自动回退上月；这两项作为讨论点列入第 15 节，不擅改现有意图文档。

HTML 管理端最小页面：成员及显示名称、昵称分段修正、总结历史、媒体描述、模型和提示词版本、任务/发送状态、群配置。接口绑定本地或受控内网并要求管理员登录；模型密钥只保存在后端配置，不发到网页。管理操作带版本号，防止旧页面覆盖较新的修改。

| code | 固定回复 |

| multiple_intents | 要求太多啦，一次说一件事。 |
| empty_input | 叫我做什么？说句话吧。 |
| invalid_date | 是今天还是明天啊，我怎么看不明白吖 |
| unsupported_date | 是今天还是明天啊，我怎么看不明白吖 |
| future_date | 嗯...还没到那一天嘛，我不是占卜师喵 |

| intention_failed | 听不懂喵 |

Main 看到 `opt=error` 后只发送对应文案，不落入 conversation，也不执行部分请求。

以上文案保留现有文件的用户修改，不替换成通用错误提示。模块级失败初稿统一使用“这次没处理好，稍后再试喵”，详细错误只写日志，不把 SQL、密钥或堆栈发送到群。

## 12. 启动、退出与超时

启动顺序：加载配置 → 检查迁移版本和数据库 → 加载语料与群配置 → 恢复未完成阶段 → 启动接收端 → 启动单 worker → 补建缺失归档任务。接收端可先提供健康接口，但数据库未就绪时 readiness 返回失败。

退出时先停止领取新任务，继续保存已接收事件；等待当前业务阶段最多 30 秒，持久化阶段后退出。不能把整条运行中任务一律改成成功。模型超时由对应模块控制，onebot 动作初稿超时 20 秒；所有外部操作必须有超时，不能永久占住队列。

## 13. 验收场景

1. 非 @ 消息入库但不调用 intention；真实 @ 触发一次任务，正文中的普通 @文字不触发。
2. 两个请求连续到达，执行串行；第一个等待 DS 时第二条消息已经入库。
3. 同一消息重复上报只生成一次任务；机器人回显不递归触发。
4. 多要求只发送“要求太多啦，一次说一件事。”，任何业务模块都不执行。
5. 02:00 请求按前一业务日计算；排队跨过 04:00 后结果日期不变。
6. 04:00 归档任务只保存数据；停机后补归档不会自动向群发总结。
7. 结果已保存而发送失败，只恢复发送；已结算福缘不重复结算。
8. memento 不直接调用 NapCat；Main 顺序上传和通知，恢复时已成功动作不重复执行。
9. 发送结果不明进入 unknown/needs_review，不自动连发多条。
10. 保存了群 A 的数据后，群 B 查询不得读出群 A 的内容或文件。

## 14. 实现顺序

先实现 receiver 的事件适配和府库消息入库，再实现基于 log 的任务队列与固定假模块分发；完成时间工具、动作日志、归档和恢复测试后接入 intention、memento、summary。conversation 和 divine 待各自方案确定再实现。网页先做只读状态页，再开放入队的修改操作。

本稿给出的默认方案已经能形成完整流程，以下项目尚未由用户逐项确认：反向 WebSocket；单 worker 的租约/重试数值；公共结果结构；长消息切分；归档 JSONB 大小与后续分卷；语料文件冲突恢复；管理端登录方式；D日/D号补全年月规则。真实 NapCat 能力通过联调验证，不把文档假设写成已验证事实。
